---
title: Tailscale
description: How catch gets a tagged identity and how services get their own tailnet nodes.
---

Yeet uses Tailscale in two places:

- catch exposes host access through an embedded Tailscale node.
- Services can get their own Tailscale identity with `--net=ts`.

Catch joins your tailnet, but the local `yeet` CLI does not run its own
Tailscale client. Normal `yeet` commands use HTTP and WebSocket connections to
the catch hostname, so your workstation must have network reachability to that
Tailscale address. In the standard setup, install Tailscale on the workstation
and connect it to the same tailnet. Commands that query local tailnet state,
such as `yeet list-hosts`, also use the local Tailscale client API.

There are two separate questions here: can your workstation reach catch, and
what is the caller allowed to do after it reaches catch? Tailscale handles both
layers, but they fail differently.

## Yeet OS installer

For a machine named `minilab`, use `ssh yeet@minilab` for a regular shell and
`yeet --host=yeet-minilab status` to manage deployments. The installer lets you
choose both names. A single OAuth client with **Auth Keys write** enrolls the
two devices and supplies a separate one-time key for each new service. In the
policy example below, also add `"tag:yeet-host": ["tag:yeet"]` to `tagOwners`.
Grant your operators TCP 22 on the machine tag and grant app clients the ports
they need on the service tag. Enable MagicDNS to reach devices by name.

With automatic service enrollment selected, `yeet run web nginx:alpine`
uses `svc,ts` and the installer's service tag. An explicit `--net=svc` keeps
that service private to Yeet. Existing services retain their networking.
A VM has its own guest operating system and controls its own Tailscale login.
The installer also offers Yeet-server-only setup for browser sign-in or an auth key.

## First-time host setup

Catch must join your tailnet as a tagged node, usually `tag:catch`. Catch
rejects user-owned nodes.

Before installing Yeet OS, set up Tailscale in this order:

1. Add a yeet owner tag, such as `tag:yeet`.
2. Let that owner tag own the catch tag, usually `tag:catch`.
3. Let that owner tag own any service tags you plan to use later, such as
   `tag:app`.
4. Open `Trust credentials` -> `Credential` -> `OAuth` in the Tailscale admin
   console.
5. Choose `All - Read & Write` for a simple broad credential, or choose custom
   scopes with Auth Keys write (`auth_keys`) for least privilege.
6. For catch-only installs, select `tag:catch` directly. For future service
   `--net=ts`, select the owner tag, such as `tag:yeet`, so the credential can
   create keys for `tag:catch` and service tags such as `tag:app`.
7. Copy the `tskey-client-...` OAuth client secret.

Paste the secret in the installer’s Tailscale setup screen.
Validate the host with `yeet status`.

Minimal policy shape:

```jsonc
{
  "tagOwners": {
    "tag:yeet": ["autogroup:admin"],
    "tag:catch": ["tag:yeet"],
    "tag:app": ["tag:yeet"],
  },
  "grants": [
    {
      "src": ["autogroup:admin"],
      "dst": ["tag:catch"],
      "ip": ["tcp:41548"],
      "app": {
        "yeetrun.com/app/yeet": [{ "allow": ["read", "manage", "ssh"] }],
      },
    },
    {
      "src": ["tag:catch"],
      "dst": ["tag:catch"],
      "ip": ["tcp:41548"],
    },
  ],
}
```

The first grant lets Tailscale admins run the first setup and normal admin
commands. See [Tailscale Access Grants](/docs/security/tailscale-access-grants)
for the `read`, `manage`, and `ssh` permissions attached to that grant.
Keep `autogroup:admin` directly in the grant `src`; do not put it inside a
custom policy-file group.

The catch node joins as `tag:catch`. With the least-privilege owner-tag setup,
the OAuth client uses `tag:yeet` only so it can mint auth keys for `tag:catch`
and later service tags.

If you are comfortable with broad Tailscale API access, `All - Read & Write` is
the simplest OAuth scope choice. If you do not plan to use `--net=ts` for
services, a least-privilege OAuth client can assign `tag:catch` directly. The
owner-tag pattern is more flexible because the credential can mint the future
service tags you deliberately allowed.

## Host naming

Choose the machine and Yeet server names in the installer. For a machine named `minilab`, use `ssh yeet@minilab` for a shell and `yeet --host=yeet-minilab status` to list apps. Use a distinct name for each tailnet device.

## Service networking (`--net=ts`)

Use `ts` when a service should get its own tailnet identity, tailnet IP, tags,
ACLs, or Tailscale Serve config.

For most services, use `svc,ts` instead of plain `ts`:

```bash
yeet run <svc> ./compose.yml --net=svc,ts --ts-tags=tag:app
```

`svc,ts` keeps yeet DNS, private service-to-service traffic, and ordinary
internet egress through the catch host. It also gives the service its own
Tailscale identity.

Use plain `ts` only for deliberately tailnet-only services:

```bash
yeet run <svc> ./compose.yml --net=ts --ts-tags=tag:app
yeet ip <svc>
```

Plain `ts` does not provide ordinary outbound internet by itself. Configure an
exit node when a `ts`-only service needs internet access:

```bash
yeet run <svc> ./compose.yml --net=ts --ts-tags=tag:app --ts-exit=<exit-node>
```

For an existing Tailscale service, update the desired exit node through
`service set`:

```bash
yeet service set <svc> --ts-exit=<exit-node>
yeet service set <svc> --ts-exit=
```

Use `iso,ts` when an isolated container-backed service needs both public IPv4
egress and its own tailnet identity:

```bash
yeet run <svc> ./compose.yml --net=iso,ts --ts-tags=tag:app
```

Ordinary traffic still uses iso's Catch NAT, while tailnet routes and MagicDNS
use the service-owned Tailscale interface. Selecting `ts` is an explicit
exception to iso's otherwise public-internet-only policy. VMs do not support a
Yeet-managed `iso,ts` mode; install Tailscale inside the guest instead.

Make sure the OAuth client saved during catch setup can assign every tag you
pass with `--ts-tags`. If the credential cannot mint the tag, deployment fails.

Use `yeet run` network flags when creating the service. Change an existing
non-VM service through `yeet service set`:

```bash
yeet service set <svc> --net=ts --ts-tags=tag:app
yeet service set <svc> --ts-exit=<exit-node>
yeet service set <svc> --ts-exit=
```

`--net` replaces the complete mode set. The other supplied Tailscale flags
patch one setting, and an explicit empty value clears tags, version, or exit
node. Omitted values stay unchanged. Whenever the resulting modes include
`ts`, the resulting tag list must be non-empty; existing valid tags can be
inherited. Yeet uses `--ts-auth-key` only for the current enrollment and never
shows it in info output or saves it to `yeet.toml`.

To add a Tailscale identity to an existing LAN service while keeping LAN
access, include both modes:

```bash
yeet service set <svc> --net=lan,ts --ts-tags=tag:app
```

This also applies to services on custom paths or ZFS datasets. The service
root and payload stay in place. Catch checks the replacement Tailscale
configuration before stopping the current service; if that check fails, it keeps
running with its previous network settings.

Options:

- `--ts-tags=<tag>` sets service tags. Repeat it to replace the list with
  multiple tags.
- `--ts-exit=<node>` uses a Tailscale exit node.
- `--ts-ver=<ver>` selects a Tailscale version for the service.
- `--ts-auth-key=<key>` passes a transient, write-only auth key for the
  operation.

See [Networking](/docs/concepts/networking) for when to choose `svc`, `lan`,
`ts`, `iso`, or a combination.

## Tailscale commands for a service

Run Tailscale commands for a service identity:

```bash
yeet tailscale <svc> -- status
yeet ts <svc> -- debug daemon-logs
```

Update the yeet-managed service Tailscale binary:

```bash
yeet ts <svc> update
yeet ts <svc> update --version=1.95.112
```

If you intentionally want Tailscale's own upstream `update` subcommand, pass it
through after `--`:

```bash
yeet ts <svc> -- update
```

## Tailscale Serve

Expose a service over HTTPS on your tailnet:

```bash
yeet ts <svc> serve --bg 3000
```

Serve requires tailnet HTTPS. With `--bg`, the Serve config persists across
reboots.

## Cleanup

When you remove a service, yeet attempts to delete that service's Tailscale
device from your tailnet. Cleanup matters because old service identities are
old access paths.
